一页结论

给评审者的最短版本：现状判断、升级主线与本次交付边界。

现状判断

能用，但不够可信

站点已经完成“每天自动更新 + 多语言榜单 + 静态部署”的闭环，但仍是一个每日被覆盖的展示页，无法回答“数据全不全、相比昨天发生了什么”。

升级主线

可信 → 高效 → 可触达

先让数据可追溯、异常可见，再提升发现效率（趋势、检索、详情），最后用 RSS 与分享把一次性访问变成持续触达。

交付边界

9 项 P0，3 个阶段

保持纯静态、零账号、机器排序；不引入后端与个性化推荐。P1 能力在 P0 稳定后按反馈排期。

核心决策：本次升级不改变“轻”的产品形态，而是把数据管道做成有历史、有校验、有降级的基础设施，再用检索与趋势标识把它变成真正的“趋势日报”。
要解决的问题对应能力里程碑
数据每日覆盖、缺失无感知、失败不可见快照与完整性校验、状态矩阵、维护者告警阶段一
只能逐条肉眼浏览，无法快速定位时间窗、趋势标识、检索/排序/筛选、详情展开阶段二
只能主动打开站点，分享无法还原视图RSS、可分享 URL、无障碍与多端完善阶段三
01

背景与现状

以下现状来自当前仓库代码与 2026-11-09 的数据快照，不包含推测。

1.1 产品当前形态

项目是一个部署在 GitHub Pages 上的纯静态站点，无后端、无构建步骤。页面读取 data/trending.js，展示总榜与 Python、JavaScript、TypeScript、Go、Rust、Java 六个语言榜；条目包含排名、仓库名、简介、语言、Star、Fork 与“今日新增 Star”。

数据由 fetch-trending.mjs 抓取 GitHub Trending 页面生成，失败时回退到 GitHub Search API；update.yml 每天 UTC 00:00（北京时间 08:00）运行，提交数据并部署 Pages，也支持手动触发与 push 触发。

已有优势：零运行成本、打开即读、每日自动更新、具备页面骨架与失败兜底、已做基础响应式与“减少动态效果”适配。这些是升级必须保留的资产。

1.2 当前数据观察

观察项2026-11-09 快照说明
总榜条目数9 条与“每日热门总榜”的预期容量存在明显差距，页面没有完整性提示。
语言榜条目数4–18 条各榜数量差异大，用户无法判断是真实结果还是抓取缺失。
数据生成时间04:50 UTC（12:50 北京）页面可显示生成时间，但页脚将更新时间写死为 08:00，两者可能不一致。
历史数据无trending.json 每次运行被整体覆盖，无法计算“新上榜 / 上升 / 连续在榜”。
数据来源全部为页面抓取本次未触发 API 兜底；兜底路径缺少完整性校验与告警。

上述数字只用于说明现状，不作为长期质量指标；实际容量取决于 GitHub Trending 页面本身。

1.3 观察到的问题

编号现象对用户的影响当前证据
P-01每日数据覆盖，没有历史快照无法回看、无法解释“为什么今天值得看”，也无法生成趋势标识抓取脚本只写最新 trending.json
P-02缺少条目数与字段完整性校验抓取缺漏时用户看到的是一份“看起来正常”的不完整榜单总榜仅 9 条；脚本只判断结果是否为空
P-03只有榜单切换，没有检索、排序、筛选榜单变长后只能逐条扫读，找不到特定项目或主题app.js 仅渲染分类标签与列表
P-04条目信息浅需要先跳到 GitHub 才能判断是否相关，增加决策成本仅有描述、语言、Star、Fork、今日新增
P-05失败状态不可见抓取失败或使用兜底数据时，用户只看到“数据不可用”或毫无提示仅覆盖无数据与示例数据两种状态
P-06触达方式单一用户必须主动打开站点，无法订阅或被动接收无 RSS、摘要或分享入口
P-07视图状态不进入 URL无法分享“Python 周榜 + 搜索某个主题”的具体视图分类状态只存在内存中
P-08语义与分享元数据不完整键盘用户与屏幕阅读器体验受限；社交平台无法生成有效预览分类按钮使用 aria-pressed 而非 tab 语义；无 OG 元数据
P-09缺少数据契约与自动化测试页面结构变化时可能静默产出错误数据无测试、无 lint、无数据校验步骤

1.4 约束条件

必须在以下约束内设计：静态托管（GitHub Pages）、无自有后端、零用户账号、依赖 GitHub Actions 免费额度、数据源为公开页面与公开 API、维护者以个人为主。任何需要常驻服务、数据库或登录体系的方案不进入本次范围。

同时保留三项产品原则：不做人工编辑榜单，不插入付费排序，不把缺失数据伪装成 0。

02

产品契约

明确“为谁、在什么时刻、完成什么”，后续需求均以此为准。

契约项定义
主用户中文开发者：每天想用最少时间发现值得关注的开源项目，关注 AI、基础设施、前端与工具链。
次用户技术选型者、开源爱好者、内容创作者；维护者作为运营角色，负责数据质量与发布。
核心任务在 3 分钟内判断“今天哪些项目值得点开”，并理解它为什么出现在榜单上。
触发时刻早晨通勤、午休、工作间隙打开站点；或通过 RSS / 分享链接进入。
完成条件用户点开至少一个 GitHub 仓库，或收藏/分享/订阅了本次内容。
共享对象每日快照包含多个榜单，每个榜单包含多个条目；趋势、订阅与历史都围绕“快照”这一对象展开。
信任基础来源可查、生成时间可见、异常状态透明、历史数据不被失败任务覆盖。
明确不做用户账号、评论点赞、个性化推荐、人工榜单编辑、付费推广、全文 README 镜像。
产品定位一句话：一个每天更新、可回溯、可检索、可订阅的开源趋势日报，而不是一个只在当天有效的排行榜页面。
03

目标与判据

不编造增长数字，用可观察的结果描述升级是否成立。

目标可观察的成立条件
数据可信任意榜单页都能回答“何时生成、是否完整、来自哪里”；单榜失败时其余榜单可用；失败任务不会覆盖上一份有效数据。
趋势可解释每个条目可以说明“新上榜 / 上升 / 下降 / 连续在榜”，且无历史基线时明确不显示，而不是显示 0。
发现高效用户可在两次操作内把范围缩小到“某语言 + 某时间窗”；搜索可直达仓库名、描述或主题；结果为空时能一键恢复。
视图可传递榜单、时间窗、搜索、排序与筛选全部进入 URL；分享链接可在新窗口还原同一视图；提供每日可用的 RSS。
体验可达仅用键盘可完成“切换榜单 → 搜索 → 展开详情 → 打开 GitHub”；360px 宽度无横向滚动；200% 缩放不破版。
异常可恢复首次无数据、全部失败、部分失败、过期、搜索无结果、字段缺失六类情况均有明确文案与下一步操作。
验证方式：阶段一按连续 7 个更新周期检查数据与告警记录；阶段二做一次包含键盘走查的评审；阶段三用 RSS 校验器与隐私窗口分享验证。具体量化目标待上线后按真实流量设定，本文不预设。
04

范围与优先级

P0 是形成完整用户旅程的最小集合；P1 是明确延后的增强项。

4.1 P0 本次必须完成

ID能力纳入原因依赖阶段
FR-01数据快照、完整性与新鲜度没有可信数据，趋势与订阅都不成立无一
FR-07状态、异常与恢复让失败可见、可解释、可恢复FR-01一
FR-09维护者运营与数据质量保证长期运行不靠人工盯守FR-01一
FR-02榜单与时间窗让同一批数据支持日/周/月三种视角FR-01二
FR-03条目信息与趋势标识回答“今天为什么值得看”FR-01、FR-02二
FR-04检索、排序与筛选从“浏览”升级为“定位”FR-02、FR-03二
FR-05项目详情展开在站内完成相关性判断，减少无效跳转FR-03二
FR-06订阅与分享从一次性访问转为持续触达FR-01、FR-04三
FR-08可访问性与多端主流程对所有用户可用，并支撑分享传播FR-02~06三

4.2 P1 明确延后

能力延后原因
历史日期浏览与 7/30 天趋势图数据与趋势计算在 P0 已具备，用户界面可在验证需求强度后再开放
本地收藏与“我的关注”不依赖账号，但优先级低于核心发现流程
英文界面先验证中文用户的主流程，再做界面文案国际化
每日摘要（GitHub Issue / 邮件 / 飞书）RSS 已能覆盖订阅需求，摘要涉及渠道选择与内容编排
分享卡片与社交预览图需要额外生成静态图片与模板，P0 先保证链接可还原视图
更多语言榜与 PWA 离线属于容量与体验增强，不阻塞主旅程

4.3 明确不做

用户账号与云端收藏、评论与点赞、人工编辑或付费排序、个性化推荐、全文 README 镜像、自动翻译项目描述。以上能力会引入后端、审核或内容责任，与“轻量静态日报”的定位冲突。

假设：GitHub Actions 的公开仓库额度与 GitHub API 限额足以支撑每日一次、七个榜单与详情补充；若不足，详情补充按 FR-05 静默降级，不影响主列表。[Assumption, TBD]
05

升级路线

按“先可信、再高效、后触达”的依赖顺序推进；每个阶段都有可验证的退出条件。

PHASE 01

稳固数据底座

  • 每日快照与 30 天保留
  • 条目数、字段、重复项校验
  • 失败不覆盖、过期与部分可用状态
  • 工作流质量摘要与失败告警
退出条件：连续 7 个更新周期内，没有空榜覆盖有效快照；任一单榜失败时页面仍可用且状态正确；失败均有告警记录。
PHASE 02

提升发现效率

  • 日 / 周 / 月时间窗
  • 新上榜、升降、连续在榜
  • 搜索、排序、趋势筛选
  • 项目详情内联展开
退出条件：从默认页到打开任一仓库不超过 4 次操作；URL 可还原全部视图；键盘走查与 360px 宽度检查通过。
PHASE 03

建立持续触达

  • 每日总榜 RSS
  • 可分享的视图链接
  • 状态文案与恢复入口完善
  • 语义、对比度与多端收口
退出条件：RSS 通过校验器；分享链接在隐私窗口还原同一视图；过期、部分失败、无结果三种状态可手动复现。

5.1 依赖与节奏

  • 阶段二的所有趋势能力依赖阶段一的历史快照；阶段一未完成前不启动趋势开发。
  • 阶段三的 RSS 依赖“成功快照才发布”的规则；不得从示例数据生成订阅内容。
  • P1 不排入本次交付；阶段三结束后按真实反馈决定顺序，优先“历史日期浏览”与“本地收藏”。
不建议的做法：先做视觉改版或增加更多语言榜，而不解决数据完整性。那会让“看起来更丰富”的页面建立在不可信的数据上。
06

核心流程

两条主流程：访客如何完成一次发现，系统如何安全地发布一份快照。

6.1 访客发现流程

进入站点默认总榜 · 日榜 · 显示新鲜度
→
缩小范围语言 / 时间窗 / 搜索 / 趋势筛选
→
判断价值趋势标识 + 简介 + 展开详情
→
完成动作打开 GitHub / 复制链接 / 订阅 RSS

失败分支：搜索无结果时保留筛选条件并提供“清除筛选”；数据过期时保留内容并显示横幅；全部不可用时给出最近成功更新时间与重试入口。

6.2 数据发布流程

触发每日定时 / 手动 / 推送
→
抓取各榜页面优先，API 兜底，单榜独立
→
规范化与校验去重、字段缺失、条目数下限
→
生成快照历史记录 + 页面数据 + RSS
→
发布或降级成功发布 / 部分可用 / 保留上次

6.3 快照状态链

正常→ 过期→ 严重过期→ 不可用

状态由“距离最近一次成功更新的时间”决定；单榜失败不改变全局状态，而是在该榜与页面横幅上标记“部分可用”。状态定义见 9.2。

07

功能需求

九个能力共同构成完整旅程。字段、趋势、排序等跨模块规则统一见第 09 章，此处不重复定义。

FR-01

数据快照、完整性与新鲜度

P0阶段一

目标：让“这份数据是什么时候的、全不全、能不能信”在页面上有唯一答案，并为趋势判断提供历史基线。

处理规则
  1. 每个更新周期生成一份快照，标识日期（Asia/Shanghai）、生成时间、各榜条目数、各榜来源（页面抓取 / API 兜底）与完整性状态；同日多次运行以最后一次成功结果为准。
  2. 快照保留最近 30 天，超出后清理并更新历史索引；保留周期为可配置项。[Assumption, TBD]
  3. 各榜独立抓取、独立校验、独立成败；单榜失败不得导致整次任务失败，也不得用空数组覆盖该榜上一份有效数据。
  4. 总榜失败、解析为空、条目数低于下限、必填字段缺失率超阈值或出现重复条目时，该榜判为“数据不完整”，按失败处理并保留上次有效内容。[阈值 TBD]
  5. 示例数据必须显式标记为 sample，不参与趋势计算、不写入历史、不生成 RSS。
  6. 页面在任何榜单下都展示生成时间（绝对时间 + 相对时间）与状态；相对时间每十分钟刷新一次。
状态与页面表现
状态判定页面表现可用操作
正常最近一次成功更新在 1 个更新周期内绿色状态点 + “更新于 …”正常浏览
部分可用至少一个榜单失败或被判定不完整全局保持正常/过期状态，页面横幅说明受影响榜单，该榜头部标记“数据不完整”浏览其它榜单；查看上次成功时间
过期超过 1 个更新周期未成功更新黄色状态点 + 顶部横幅“当前展示最近一次可用数据”继续浏览；查看生成时间
严重过期超过 2 个更新周期未成功更新红色状态点 + 醒目横幅继续浏览；提供反馈入口
不可用没有任何可展示的有效快照空状态卡片，说明原因与最近一次尝试时间重试；查看数据源
异常与结果
  • 超时、HTTP 错误、解析为空、API 限流均按单榜失败处理；记录错误类型与受影响榜单。
  • 结果写入一份新快照，同时产出趋势基线、页面数据与订阅内容；失败时不发布空数据。
  • 任何降级都必须对用户可见，不允许静默回退。

相关规则：9.2 时间与新鲜度、9.5 去重与缺失、FR-07 异常状态、FR-09 维护者运营。

FR-02

榜单分类与时间窗

P0阶段二

目标：用同一套界面支持“总榜 + 语言榜”和“日 / 周 / 月”两个维度，让用户快速切换到自己的关注范围。

布局与触发
  • 页面顶部为榜单分类：总榜、Python、JavaScript、TypeScript、Go、Rust、Java；默认选中总榜。
  • 分类下方为时间窗切换：今日、本周、本月；默认今日。切换时间窗只改变当前榜单数据，不改变榜单选择。
  • 点击分类或时间窗立即渲染，不整页刷新；当前选择同步到 URL。
处理规则
  1. URL 参数使用 board 与 since；非法或缺失值回退默认，并保留其它有效参数，不弹错误。
  2. 浏览器的前进/后退可还原榜单与时间窗；切换不产生重复历史记录。
  3. 榜单标题随选择变化，并显示“共 N 个项目”；时间窗改变时，条目上的新增 Star 文案同步为“今日 / 本周 / 本月新增”。
  4. 某榜来自 API 兜底时，在该榜头部显示“备用数据源”弱提示；兜底数据不得伪装成页面实时数据。
  5. 移动端分类横向滚动，选中项自动滚入可视区；时间窗保持可见，不与分类争夺空间。
状态与异常
  • 加载中显示骨架行，数量与常见榜单容量一致，避免布局跳动。
  • 榜单为空：显示“本榜暂无数据”与生成时间，不隐藏分类，方便切换。
  • 单榜失败：该榜显示错误卡片与“重试”，其它榜不受影响。
  • 示例数据：页面顶部保留示例横幅，分类与时间窗仍可操作，但不得生成趋势标识。

原型：第 08 章可切换分类与时间窗。

FR-03

条目信息与趋势标识

P0阶段二

目标：让用户在一屏内判断“这个项目今天为什么值得点开”，而不是只看到一串 Star 数。

展示规则
  1. 条目固定展示：排名、仓库全名、简介（最多两行，展开后完整）、语言与色点、总 Star、Fork、当前时间窗的新增 Star。
  2. 语言色点必须同时显示语言名称，不以颜色作为唯一信息；趋势徽标同理，必须带文字。
  3. 变化标识按 9.3 计算：新上榜、↑N、↓N；连续在榜 ≥3 时额外显示“连续 N 天”。新上榜条目不再显示连续天数，避免信息冲突。
  4. 没有历史基线时隐藏变化标识，不显示“0”或“—”。新增 Star 缺失时隐藏该项，不按 0 处理。
  5. 排名从 01 开始补零；前三名使用金、银、铜强调，但不得只靠颜色区分，屏幕阅读器读取“第 N 名”。
  6. 点击仓库名在新标签页打开 GitHub；展开详情使用独立按钮，避免整行链接与文本选择冲突。
  7. 简介保持源语言，不做自动翻译；中文界面文案与项目原文并存。
排序与标识优先级
  • 默认按榜单原始排名展示；任何其它排序都不改变排名数字，只改变显示顺序。
  • 变化标识与连续标识同时存在时，变化标识在前；移动端空间不足时优先保留变化标识。
  • 备用数据源条目通常缺少新增 Star 或趋势基线，按缺失规则隐藏，不推断。

字段定义：9.6 字段字典；趋势算法：9.3。

FR-04

检索、排序与筛选

P0阶段二

目标：把“逐条扫读”变成“直接定位”，并让筛选后的视图可以被分享和还原。

检索
  • 搜索范围：仓库所有者、仓库名、简介、主题（topics）、语言；忽略大小写与首尾空格。
  • 输入停顿 300ms 后过滤；中文输入法组合输入期间不触发，避免拼音阶段产生闪烁。
  • 按 / 聚焦搜索框；Esc 清空搜索并恢复完整列表；提供可见的清空按钮。
  • 结果数量通过礼貌级 live region 播报；无结果时展示“没有符合条件的项目”与“清除筛选”。
排序与筛选
  • 排序项：榜单排名（默认）、当前时间窗新增 Star、总 Star；排序稳定，数值相同按原始排名。
  • 趋势筛选为单选：全部、新上榜、排名上升、连续在榜；每个筛选项显示当前榜单内的数量。
  • 总榜额外提供语言筛选；语言榜内不重复提供语言筛选。
  • 搜索、筛选、排序之间为“与”关系；筛选条件变化后结果为空时，保留条件并提供一键重置。
URL 与状态
  • 参数：q、sort、trend、lang，与 board、since 共同构成完整视图。
  • 默认值不写入 URL，保持链接简洁；非默认值可被分享与还原。
  • 刷新或从分享链接进入时，先还原筛选再渲染列表，避免先闪全量再收敛。

统一规则：9.4 排序、筛选与 URL；原型：第 08 章可直接体验。

FR-05

项目详情展开

P0阶段二

目标：在列表内补齐“是否与我相关”的关键信息，减少一次无效跳转。

交互规则
  • 每条目提供“详情”按钮，内联展开，不使用弹窗；同一时间最多展开一条，展开另一条时自动收起上一条。
  • 展开按钮使用 aria-expanded 表达状态；Esc 收起当前详情并保持焦点在按钮上；切换榜单或筛选导致条目消失时自动收起。
  • 展开不改变列表顺序，不触发二次加载；详情数据随快照一起就绪，不出现行内 spinner。
内容字段
字段展示缺失处理
完整简介取消两行截断，显示原文显示“暂无项目简介”
主题 Topics标签组，最多展示 8 个不显示该区块
许可证许可证名称，如 MIT、Apache-2.0显示“未标注”
项目主页可点击的外部链接，标注“项目主页”不显示
最新 Release版本号 + 发布时间显示“暂无 Release 信息”
快捷操作打开 GitHub、复制仓库链接、分享始终可用
异常与降级
  • 详情补充信息在构建期获取；获取失败时仅展示列表已有字段，不向用户报错，也不阻塞主列表。
  • 仓库可能已迁移或删除时，详情中提示“该仓库可能已迁移或删除”，GitHub 链接仍保留。
  • 主题等内容超出数量上限时截断，不提供“展开更多”，避免详情无限增长。

字段来源与缺失规则：9.5、9.6；原型：第 08 章点击“详情”。

FR-06

订阅与分享

P0阶段三

目标：让用户不必每天主动打开站点，也能收到当日结果；让一次筛选结果可以被完整传递。

分享
  • 分享范围是“当前完整视图”：榜单、时间窗、搜索词、排序、趋势筛选、语言筛选。
  • 优先调用系统分享面板；不支持时复制链接。复制成功给出短暂提示，失败时展示可手动复制的输入框。
  • 分享链接不包含用户标识、来源追踪参数或个人信息；在隐私窗口打开应还原同一视图。
  • 仓库维度提供“复制仓库链接”，分享内容为 GitHub 地址，不附带站点参数。
RSS
  • 提供每日总榜订阅源 /feed.xml；仅由成功快照生成，示例数据与失败任务不生成内容。
  • 频道包含站点名、站点链接、一句话说明、数据生成时间；每条内容包含仓库全名、简介、语言、新增 Star、GitHub 链接与稳定 GUID。
  • 内容数量与总榜一致；排序与榜单一致；订阅源保留最近一次成功内容，不因抓取失败而清空。
  • RSS 生成失败不得阻塞页面发布，但必须触发维护者告警。
延后项

按语言拆分订阅源、每日摘要（GitHub Issue / 邮件 / 飞书）、分享预览图属于 P1；P0 只保证“链接可还原、RSS 可用”。

URL 参数：9.4；原型：第 08 章“复制链接 / RSS”演示了反馈方式。

FR-07

状态、异常与恢复

P0阶段一

目标：每一种失败都能被用户理解、被用户绕过、被维护者发现。

状态矩阵
场景用户看到页面行为下一步
首次无数据空状态卡片：尚无可用快照保留页头、分类与页脚，不显示假数据查看数据源；稍后重试

部分榜单失败顶部横幅列出受影响榜单失败榜显示错误卡片，其它榜正常切换其它榜；重试失败榜
数据过期黄色/红色状态 + 横幅继续展示旧数据，明确标注时间继续浏览；查看生成时间

恢复与告警
  • 页面提供“重新加载”动作；过期状态下仍可继续阅读，不强制阻断。
  • 失败任务更新一个固定标题的告警 Issue，包含受影响榜单、错误类型、运行链接与最近成功时间；下一次完整成功后自动关闭。
  • 不允许出现“无提示回退”“空榜覆盖”“永久加载骨架”三种静默失败。

状态定义：9.2；告警流程：FR-09。

FR-09

维护者运营与数据质量

P0阶段一

目标：让站点在维护者不盯着的情况下，也能暴露问题、保留证据、快速恢复。

运行摘要
  • 每次运行输出：各榜条目数、数据来源、耗时、触发的降级、完整性校验结果与最终快照版本。
  • 摘要展示在工作流运行页面，便于复盘；不要求额外搭建监控面板。
手动触发
  • 保留手动触发，并支持选择时间窗、榜单范围与“仅校验不发布”模式，便于排查数据源问题。
  • “仅校验不发布”不得修改线上快照、历史与 RSS。
告警与审计
  • 任务失败或单榜不完整时，创建/更新固定告警 Issue；恢复后自动关闭并在 Issue 内留下恢复时间。
  • 每份快照可追溯到对应提交或运行记录；页面展示的生成时间与快照记录一致。
  • 超过保留期的快照自动清理，历史索引同步更新；清理失败不得影响最新快照发布。
权限边界

访客只读；维护者通过仓库写权限触发运行与处置告警。站点不收集访客个人信息，不接入第三方统计脚本。

状态与告警规则：9.2、FR-07；权限矩阵：9.7。

09

共享规则

跨模块的唯一口径。功能章节只引用，不重复定义。

9.1 术语

术语定义
更新周期站点约定的数据刷新间隔，默认 1 天；调整周期会同步影响新鲜度判定，但本文档不改变当前每日一次的频率。
每日快照某个日期下所有榜单的完整结果集合，包含生成时间、来源、完整性与条目。趋势与订阅都以快照为单位。
榜单由“时间窗 + 范围”唯一确定的列表，例如“日榜 · Python”。总榜是范围最广的榜单。
条目榜单中的一个仓库，包含排名、仓库信息、指标与趋势标识。
基线用于计算趋势的上一个同范围、同时间窗的有效快照；示例数据、无效快照不作为基线。
有效快照至少总榜通过完整性校验、且未被标记为示例数据的快照。

9.2 时间与新鲜度

  • 所有面向用户的日期时间以 Asia/Shanghai 展示；数据记录同时保留 UTC 生成时间，便于追溯。
  • 生成时间展示为“2026-11-09 08:00（北京时间）”与“2 小时前”两种形式；相对时间在页面停留期间每十分钟刷新。
  • 新鲜度以“距最近一次成功更新”的周期数判定：≤1 个周期为正常；>1 且 ≤2 为过期；>2 为严重过期；无有效快照为不可用。
  • “部分可用”是并列状态而非时间状态：只要存在失败或被判不完整的榜单就显示，直到下一次完整成功。
  • 示例数据不参与新鲜度计算，页面始终显示“示例数据”而不是“正常”。

9.3 趋势计算

标识计算方式显示
新上榜基线中不存在该仓库，本次出现在同一榜单蓝色“新上榜”
上升基线存在，且本次排名数字小于基线排名绿色“↑N”，N 为名次提升值
下降基线存在，且本次排名数字大于基线排名红色“↓N”，N 为名次下降值
持平基线存在且排名相同不显示排名变化；若连续天数 ≥3，显示连续标识
连续在榜从最近一次快照向前，连续有效快照中均出现的次数“连续 N 天”；周榜/月榜按对应快照周期表述
  • 基线必须同榜单、同时间窗；日榜不与周榜比较，Python 榜不与总榜比较。
  • 没有基线、基线无效或当前数据为示例数据时，所有趋势标识隐藏。
  • 新上榜不显示连续天数；连续天数至少为 3 才展示；展示数量最多为“变化标识 + 连续标识”两个。
  • 趋势只描述排名与在榜状态，不推断质量、热度或商业价值。

9.4 排序、筛选与 URL

参数含义默认非法值处理
board榜单范围：all / python / javascript / typescript / go / rust / javaall回退 all，保留其它参数
since时间窗：daily / weekly / monthlydaily回退 daily
q搜索词，最长 80 字符空截断并去除首尾空格
sortrank / growth / starsrank回退 rank
trendall / new / up / streakall回退 all
lang仅总榜使用的语言筛选空语言榜内忽略
  • 筛选组合为“与”；排序不改变排名数字；排序稳定性以原始排名作为最终比较键。
  • 默认值不写入 URL；仅非默认值参与分享，避免链接冗长。
  • 页面初始化时先解析 URL 再渲染，避免“先全量后收敛”的闪烁。
  • 搜索忽略大小写与首尾空格；匹配仓库所有者、名称、简介、主题与语言。

9.5 去重与缺失

  • 同一榜单内按仓库全名去重，忽略大小写；重复时保留排名更高的一条，并记录一次异常用于完整性校验。
  • 仓库所有者与名称以 GitHub 返回值为主，不使用页面展示别名。
  • 数值字段缺失时隐藏该字段，不显示 0，不显示“—”占位；文本字段缺失时使用明确的占位文案。
  • 简介为空的条目仍可参与排名与搜索，但不得生成“今日新增”之外的推断信息。
  • 语言未知时显示“未知语言”，色点使用中性灰，不猜测语言。

9.6 字段字典

字段含义必填展示与降级

9.7 权限与数据边界

角色可查看可操作数据边界
访客所有公开榜单、详情、RSS、分享链接浏览、搜索、筛选、分享、订阅不登录、不采集个人信息；本地偏好仅存于浏览器

9.8 内容与来源

  • 榜单顺序来自数据源的机器排序，不人工调整、不出售位置；任何人工干预都不在 P0 范围内。
  • 项目简介保留原文，不做自动翻译；界面文案中文化。
  • 示例数据、备用数据源、过期数据必须在对应位置显式标注，不使用模糊措辞。
  • 每个页面保留 GitHub Trending 来源链接；RSS 与分享内容同样注明来源与生成时间。

风险与对策

升级把更多能力建立在自动抓取之上，必须先承认数据源与静态托管的风险。

风险影响对策
GitHub Trending 页面结构变化解析结果为空或字段错位，榜单不可信API 兜底、条目数与字段完整性校验、失败不覆盖、告警 Issue
GitHub API 限流或超时详情字段缺失，趋势基线不足详情静默降级；主列表与已有字段不受影响；不因补充信息失败而阻断发布
快照体积随保留期增长仓库变大、部署变慢30 天保留与自动清理；只保留展示与趋势所需字段
定时任务延迟或失败用户看到旧数据却不知情新鲜度状态、过期横幅、最近成功时间、失败告警
趋势被误读为质量评价用户把“上升”理解为“更好”只描述排名与在榜事实；不生成推荐语或质量结论
内容与商标边界转载简介或使用 Logo 引发争议保留原文并注明来源；不使用仓库 Logo；不做全文 README 镜像
